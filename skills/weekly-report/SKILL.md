# 周报生成

## 这个 skill 解决什么

周报条目里有两类内容:

1. **代码改动**:在 `oneos-multi-*` 仓库里的提交/未提交改动,能从 git 抓。
2. **非代码工作**:性能指标、onebus 合并评估、提测文档、跨团队沟通、代码 review 等,git 里**没有**,靠用户口头补充。

这个 skill 负责把代码改动从 git 里干净地捞出来、按用户一贯风格转写成草稿条目,然后在确认环节问用户补充非代码工作。**不替用户编造非代码内容。**

周报本身是**单一编号列表**,代码条目和非代码条目混在一起,不强制分段。用户过去每周给的示例有时写成两段,那只是随手分了块,不是固定结构——不要硬凑成"上段代码、下段其它"。

## 用户周报的风格(必须遵守)

中文、编号列表。格式:

```
<日期,如 9.18>
1.<条目,一句话讲清改了什么 + 为什么 + 关键技术点>
2.<条目>
3.<条目>
...
```

每条要点:
- **一句话讲清"做了什么 + 为什么"**。不写"修复了XX问题",要写"修复 mnt_ns 中 fs_rec 悬空指针崩溃:释放后置空外层指针并在取 fd 前加 NULL 守卫"——动作 + 对象 + 根因/目的。
- 技术细节要具体到模块和机制:比如"semaphore 替换为 sticky event""irqsave 方案""poll_notify 持 driver 锁期间 post"。不要泛化成"优化了性能"。
- 代码改动、测试、评估、文档、沟通这些条目可以混在同一个编号列表里,顺序按用户表达习惯,不强求分段。用户给的示例里有时分两段,有时一段,是随手分的,不是模板。

完整示例见 `references/weekly-style-example.md`(写草稿前读一遍校准风格)。

## 执行流程

### 第 0 步:确认 git 身份配置(仅首次需要)

脚本用 `--author` 过滤本人提交,author 取自 `references/git-author.conf`(不入仓库,含个人信息)。先跑脚本看配置在不在:

```bash
bash <skill-path>/scripts/gather_commits.sh
```

如果脚本输出"配置缺失"(author 或 repo_root 没定义),停下来问用户两件事:

1. 你在这些仓库里提交用的 git 用户名/email 是什么?(不确定就让用户在任一仓库跑 `git config user.name` / `git config user.email`)
2. 你的 `oneos-multi-*` 仓库根目录在哪?

拿到答案后,写入 `<skill-path>/references/git-author.conf`,两行:

```
author=<用户名或 email>
repo_root=<仓库根目录绝对路径>
```

`references/git-author.conf.example` 是模板,可参考格式。写完再跑脚本。这个配置只做一次,以后直接进第 1 步。

**不要把用户名硬编码进 SKILL.md 或脚本**——这份 skill 入公共仓库,个人身份只能存在被 .gitignore 排除的本地配置里。

### 第 1 步:抓取 git 改动

跑脚本(脚本的写法已经处理了"别人合并提交混进来"的坑,详见下方"已知坑"):

```bash
bash <skill-path>/scripts/gather_commits.sh
```

默认抓**本周一至今天**本人(配置里的 author)的提交。需要换范围时传参:

```bash
bash <skill-path>/scripts/gather_commits.sh 2026-09-01 2026-09-21
```

脚本会遍历 `oneos-multi-*` 所有 git 仓库,输出每个仓库里本人本周的提交(已排除 Merge 提交)+ 工作区未提交改动。

**空抓处理(fallback 规则,重要)**:脚本报"未抓到本人提交"时,按这个顺序处理,不要让模型自由发挥:

1. 先看输出有没有"未提交改动"(`git status` 部分),那些也算本周工作,先收着。
2. **自动用"最近 7 天"重跑一次**: `bash <skill-path>/scripts/gather_commits.sh <7天前的日期> <今天>`。空抓最常见的原因是周一当天写周报——"本周一至今天"在周一当天只覆盖今天,必然空。而用户周报日期历来是周一,报的其实是上周的工作,所以 fallback 到最近 7 天才对得上用户真实的工作周期。
3. fallback 后明确告诉用户:"默认本周一至今无提交,已自动扩大到最近 7 天(<起>~<止>)"。
4. 如果最近 7 天还是空,再问用户要不要指定起止日期或更大范围。**不要**为凑内容把别人的提交算进来。

注意脚本退出码:`0`=抓到内容,`1`=空抓,`2`=配置缺失。看到 `2` 回第 0 步。

fallback 到最近 7 天后,抓到的提交可能是上周的——这些提交**可能已经在上一期周报里报过**。这引出第 2 步的日期标注要求。

### 第 2 步:分析提交,转写成周报风格

读脚本的输出。每条 commit 的 subject 通常是 `type(scope): description` 的 conventional commit 格式,但**周报里不照搬 subject**。要做转译:

- `fix(mnt_ns): guard fs_rec NULL deref and nullify after process_vfs_deinit free`
  → 周报: `修复 mnt_ns 中 fs_rec 悬空指针崩溃:process_vfs_deinit 释放 fs_rec 后置空外层指针,并在取 fd 前加 NULL 守卫,防止悬空访问触发对齐错误。`
- `refactor(mnt_ns): replace pty semaphores with sticky events to fix lost wakeups`
  → 周报: `将 PTY 子系统的 semaphore 替换为 sticky event,解决丢失唤醒问题。`

转译规则:
- 英文 subject → 中文,主谓宾完整。
- `fix` → "修复XX:根因/做法",`feat` → "新增XX",`refactor` → "重构XX,目的",`test` → "新增/编写XX测试用例",`chore` 一般不进周报除非重要。
- 同一模块同一主题的多个小提交(比如同一天三条 fix(mnt_ns))可以**合并成一条**,讲清这组改动的整体意图,而不是列三条碎片。用户周报里很少一个模块列超过 4 条。
- 提交 subject 信息不够时(比如只写了 "fix: xx"),**不要编**技术细节。要么照 subject 直译,要么在确认环节问用户补细节。

**日期标注与查重(重要)**:草稿里每条从 commit 转写的条目后面**标上 commit 日期**(用 ` — 9.11` 这样的短日期)。为什么:用户周一写周报,fallback 到最近 7 天后抓到的提交可能上周就报过了。用户看着带日期的草稿,对照 `references/weekly-style-example.md` 里的历史周报,能一眼判断哪条新报、哪条重复。转写时顺手标日期,确认环节问用户要不要剔除已报过的。

如果脚本输出里 fallback 抓到的提交全部落在上一期周报的日期区间内(比如这周一抓到的是上周的提交,而上一期周报已覆盖),**主动提醒用户**:"抓到的提交都在上一期(<日期>)周报范围内,本周可能只有未提交改动,要不要按未提交改动来写,或者你手动说明本周新做了什么。"

非 commit 转写的条目(未提交改动、用户口头补充的非代码工作)不需要标日期。

### 第 3 步:给出草稿,和用户确认

把草稿直接贴在对话里(不要写文件,除非用户要求)。草稿结构:

```
## 草稿(<日期>)

<日期>
1. <从 commit 转写的条目> — <commit 日期,如 9.11>
2. <从 commit 转写的条目> — <commit 日期>
3. <非代码工作 — git 抓不到,等你补充>
...
```

然后**明确问用户三件事**:
1. 草稿里的代码条目有没有要合并/拆分/补细节的?(用户最清楚技术细节,git subject 可能太粗)另外每条标了 commit 日期,对照上一期周报看有没有重复报过的,要剔的告诉我。
2. 这周有哪些非代码工作(性能指标/测试/文档/评估沟通/code review)?逐条说,我来转成周报条目。
3. 有没有本周做了但还没提交的工作?(脚本只抓得到已提交 + 工作区改动,没 add 的想法/沟通/评估抓不到)未提交改动具体在做什么,要写进周报的话给我一句话说明。

等用户回答,合并进同一个编号列表。

### 第 4 步:输出最终版

用户确认/补充后,输出干净的最终周报(只留周报正文,去掉"草稿"标记、日期标注和确认问题)。**输出即最终交付**——纯文本编号列表,直接能贴出去。条目顺序按用户确认的样子,不强求分段。

如果用户没说要存文件,就不存。要存的话,默认放 `repo_root`(git-author.conf 里那个)下的工作记录目录;不确定就问用户存哪,不要假设路径。命名 `周报-YYYY-MM-DD.md`。

## 已知坑(为什么脚本/流程这么设计)

1. **别人合并提交混进来**:os 仓库常驻个人特性分支(如 mnt_ns),裸 `git log` 会把同事合并进来的提交也带出来。脚本用 `--author=<配置里的用户名> --no-merges` 过滤,**只留本人的实质改动**。这是为什么不能直接让模型跑 `git log` 而要用脚本。author 取自配置文件而非硬编码——个人身份不入公共仓库。

2. **本周刚开始可能没提交**:周报日期是周一,但周一当天往往还没提交。脚本会提示"未抓到本人提交",流程里要走扩大范围或靠未提交改动,不要硬凑。

3. **非代码工作 git 抓不到**:性能指标实测数值、onebus 合并评估、提测文档、跨团队沟通、code review——这些不在 oneos-multi-* 仓库里。skill **不编造**这些内容,只在确认环节问用户。

4. **多仓库混合汇总**:bsp/cmake/os/user 四个仓库的提交按日期混合成一个时间线,不按仓库分组。这样更贴近用户过去周报的整体观感。脚本输出带仓库名标注,模型汇总时去掉仓库名只留日期+内容。

## 调用方注意

- 用户说"写周报"就触发,不需要用户显式提 git。
- 抓取和分析用 Bash 跑脚本,**不要**自己手写 `git log` 命令散跑——脚本已经处理了 author 过滤(取自配置)和 Merge 排除,手跑要么把别人提交算进来,要么硬编码 author。
- 配置缺失(脚本退出码 2)时先走第 0 步问用户、写配置,再抓取。**绝不**为了跳过询问把用户名直接写进 SKILL.md 或脚本。
- 风格校准:动笔前读 `references/weekly-style-example.md`。
